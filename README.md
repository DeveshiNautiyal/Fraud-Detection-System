#  Financial Fraud Detection System

A full-stack Machine Learning web application that predicts whether a
financial transaction is **Genuine** or **Fraudulent**, trained on a real,
1.85-million-row Kaggle dataset. Built as a placement/major project for
B.Tech CSE, with a live, auto-refreshing dashboard.

Live Demo : https://fraud-detection-system-i7j0.onrender.com/batch-predict

---

## Project Overview

This project demonstrates a complete, production-style ML pipeline:

1. Load and clean 1.85M+ real transaction records
2. Engineer meaningful features (customer age, customer-merchant distance,
   transaction hour/day) from raw timestamps and GPS coordinates
3. Encode categorical data and scale numeric features
4. Train and compare 4 classification models, properly handling severe
   class imbalance (~0.5% fraud)
5. Select the best model by F1-Score and serve it through a Flask web app
6. Log every prediction to SQLite and display it on a **live, auto-refreshing
   dashboard**

## Dataset

**[Credit Card Transactions Fraud Detection Dataset](https://www.kaggle.com/datasets/kartik2112/fraud-detection)**
by Kartik Shenoy (Kaggle) — a simulated but realistic dataset of 1.85 million
transactions (`fraudTrain.csv` + `fraudTest.csv`) with genuine, human-readable
columns:

| Column | Description |
|---|---|
| `trans_date_trans_time` | Timestamp of the transaction |
| `merchant`, `category` | Merchant name and spending category |
| `amt` | Transaction amount |
| `first`, `last`, `gender`, `dob` | Customer identity/demographics |
| `street`, `city`, `state`, `zip`, `lat`, `long` | Customer address & location |
| `city_pop` | Population of the customer's city |
| `job` | Customer's occupation |
| `merch_lat`, `merch_long` | Merchant's location |
| `is_fraud` | Target label (0 = Genuine, 1 = Fraud) |

Only ~0.58% of transactions are fraudulent — a realistic, heavily imbalanced
class distribution, which is why **F1-Score** (not accuracy) drives model
selection.

> **Note:** The raw CSVs (`fraudTrain.csv`, `fraudTest.csv`, ~490MB combined)
> are excluded from version control via `.gitignore` since GitHub isn't meant
> for files this large. Download them from the Kaggle link above and place
> them in `dataset/` before running `train_model.py`.

## Installation Steps

1. **Clone the repository**
   ```bash
   git clone <your-repo-url>
   cd fraud_detection
   ```

2. **Download the dataset** from Kaggle and place both CSVs inside `dataset/`:
   - `dataset/fraudTrain.csv`
   - `dataset/fraudTest.csv`

3. **Create a virtual environment (recommended)**
   ```bash
   python -m venv venv
   source venv/bin/activate      # On Windows: venv\Scripts\activate
   ```

4. **Install dependencies**
   ```bash
   pip install -r requirements.txt
   ```

##  How to Run

1. **Train the model** (takes a few minutes on the full 1.85M rows):
   ```bash
   python train_model.py
   ```
   This creates `fraud_model.pkl`, `scaler.pkl`, `encoders.pkl`,
   `model_columns.pkl`, `feature_defaults.pkl`, `model_summary.json`, and
   the chart images in `static/images/`.

2. **Start the Flask app**:
   ```bash
   python app.py
   ```

3. Open your browser and visit:
   ```
   http://127.0.0.1:5000
   ```

4. Use **Predict** to test a transaction, or **Dashboard** to watch live
   stats update as you make predictions.

##  Machine Learning Approach

| Step | Details |
|---|---|
| Data Cleaning | Missing values filled with median (numeric) / mode (categorical) |
| Feature Engineering | `age` (from `dob`), `distance_km` (Haversine formula between customer & merchant GPS), `trans_hour`, `trans_day_of_week` |
| Encoding | `category` and `gender` encoded with `LabelEncoder` |
| Feature Scaling | `amt`, `city_pop`, `age`, `distance_km` scaled with `StandardScaler` |
| Train/Test Split | 80/20, stratified to preserve the fraud ratio |
| Class Imbalance Handling | `class_weight='balanced'` (Logistic Regression, Decision Tree, Random Forest) and `scale_pos_weight` (XGBoost) — without this, models tend to just predict "Genuine" for everything |
| Models Trained | Logistic Regression, Decision Tree, Random Forest, XGBoost |
| Evaluation Metrics | Accuracy, Precision, Recall, F1-Score, **ROC-AUC**, **PR-AUC**, Confusion Matrix |
| Model Selection | Highest **F1-Score** — the right metric for a ~99.5% imbalanced dataset |
| Threshold Tuning | Decision cutoff optimized against the precision-recall curve to maximize F1, instead of the default 0.5 |
| Model Saving | Best model + scaler + encoders + tuned threshold saved via **Joblib** |

### Actual results (full 1.85M-row dataset)

| Model | Accuracy | Precision | Recall | F1 | ROC-AUC | PR-AUC |
|---|---|---|---|---|---|---|
| **Random Forest**  | 0.9966 | 0.616 | 0.906 | **0.733** | 0.997 | 0.886 |
| XGBoost | 0.9917 | 0.382 | 0.961 | 0.547 | 0.999 | 0.926 |
| Decision Tree | 0.9799 | 0.201 | 0.965 | 0.333 | 0.984 | 0.875 |
| Logistic Regression | 0.9470 | 0.072 | 0.771 | 0.132 | 0.864 | 0.186 |

After threshold tuning, Random Forest's F1-Score improves further to **~0.81**
at its optimal cutoff (found automatically by `train_model.py`) instead of
the default 0.5 threshold.

**Why this matters for an interview:** Logistic Regression without class
weighting predicts "Genuine" for almost every transaction and still scores
~99% accuracy — a classic imbalanced-data trap. Being able to explain *why*
accuracy is misleading here, why **PR-AUC** (not just ROC-AUC) is the right
curve to look at on rare-class problems, and how threshold tuning recovers
extra F1-Score beyond the default cutoff, is genuinely strong interview
material. See `PROJECT_HIGHLIGHTS.md` for ready-to-use talking points.

## Live Dashboard

The dashboard has two layers:
- **Static training stats** — dataset size, ROC-AUC, PR-AUC, tuned decision
  threshold, model comparison table, and chart images (confusion matrix,
  class distribution, ROC curve, precision-recall curve, feature importance)
  generated once by `train_model.py`.
- **Live stats** — total predictions, fraud/genuine counts (including a
  live Chart.js doughnut chart), and the most recent 10 predictions, pulled
  from SQLite and refreshed automatically every 4 seconds via a small
  JavaScript polling loop hitting `/api/live-stats`, with no page reload
  required.

## Batch Prediction (CSV Upload)

Beyond scoring one transaction at a time, `/batch-predict` lets you upload
a CSV of many transactions and score all of them in one go:

1. Download the sample template (`/download-sample-csv`) to see the
   expected columns: `amount, category, gender, city_pop, age, trans_hour`
2. Upload your own CSV (up to 5,000 rows per upload)
3. View a results preview in the browser, with every row logged to SQLite
4. Download the full results as a CSV (predictions + confidence per row)

Both the single-transaction form and batch upload call the exact same
`predict_dataframe()` function in `app.py`, so there's only one place the
prediction logic lives — single and batch predictions can never silently
disagree with each other.

##  Deploying Live (Render)

To get a public URL instead of running locally:

1. **Push this project to GitHub** (a public or private repo works). The
   trained model files (`fraud_model.pkl`, `scaler.pkl`, etc.) ARE included
   in the repo on purpose — the deployment host won't have your 1.85M-row
   CSVs to retrain from, so it needs the already-trained artifacts.
   The raw dataset CSVs stay excluded (`.gitignore`) since they're too large.

   ```bash
   git init
   git add .
   git commit -m "Fraud detection system"
   git branch -M main
   git remote add origin https://github.com/<your-username>/<your-repo>.git
   git push -u origin main
   ```

2. **Create a free account at [render.com](https://render.com)** and sign
   in with GitHub.

3. Click **New → Web Service**, select your repository.

4. Configure:
   - **Build Command:** `pip install -r requirements.txt`
   - **Start Command:** `gunicorn app:app`
   - **Instance Type:** Free

5. Click **Create Web Service**. Render will build and deploy — you'll get
   a public URL like `https://your-app-name.onrender.com`.

**Notes on the free tier:**
- The free instance spins down after inactivity and takes ~30-60 seconds
  to wake up on the next visit — normal for a demo, not for real traffic.
- SQLite (`fraud.db`) resets on redeploys, since Render's free tier
  filesystem isn't persistent across deploys — fine for a demo/portfolio
  project, not for production use.
