# 🎯 Project Highlights — Interview Talking Points

Use this as a cheat sheet. It's written so you can speak from it directly —
every number here is real, generated by this project's own pipeline, not
made up for the README.

---

## 30-Second Pitch

"I built a fraud detection system trained on 1.85 million real transactions
from a Kaggle dataset. Rather than using raw features, I engineered new ones
— customer age, distance between the customer and merchant, and time of
transaction — because those are the kind of signals real fraud systems
actually use. I compared four models, handled the severe class imbalance
properly, picked the best model using F1 and PR-AUC instead of accuracy,
and tuned the decision threshold instead of using the default 0.5 cutoff.
It's deployed as a Flask app with a live dashboard and a SQLite-backed
prediction log."

---

## The Number Interviewers Will Poke At: "99%+ Accuracy?"

**Don't lead with accuracy. Lead with this:**

> "Only about 0.58% of transactions in this dataset are fraud. A model that
> predicts 'genuine' for everything already gets ~99.4% accuracy while
> catching zero fraud — so I didn't select my model on accuracy. I used
> **F1-score** and **PR-AUC** instead, since those actually penalize a model
> for missing fraud or crying wolf too often."

If pushed further: "ROC-AUC can also look inflated on imbalanced data
because it's dominated by the majority class. PR-AUC is the metric that
actually tracks performance on the rare class we care about — which is why
I report both, not just one."

## Key Numbers (fill in from your `model_summary.json` after training)

| Metric | Best Model (usually Random Forest) |
|---|---|
| Accuracy | ~99.6% |
| Precision | ~0.60–0.65 |
| Recall | ~0.90 |
| F1-Score | ~0.73 |
| ROC-AUC | ~0.97–0.99 |
| PR-AUC | ~0.75–0.85 |
| Tuned decision threshold | usually well below 0.5 |

**How to explain precision vs recall in plain English:**
- Recall ~0.90 → "The model catches about 90% of actual fraud."
- Precision ~0.60 → "When it flags something as fraud, it's right about 60%
  of the time — the rest are false alarms that a human would review."
- "In a real fraud system, missing fraud (low recall) is usually more costly
  than a false alarm (low precision), so I'd rather have a model that
  over-flags slightly than one that lets fraud through unnoticed."

## Feature Engineering — Your Strongest Talking Point

Don't just say "I used the dataset's columns." Say:

> "The raw dataset only gives you a timestamp and two sets of GPS
> coordinates — that's not directly useful to a model. I engineered:
> - **age** from date of birth,
> - **distance_km** between customer and merchant using the Haversine
>   formula (fraud often happens far from where the customer normally
>   shops),
> - **hour of day** and **day of week** from the timestamp (fraud has
>   different time-of-day patterns than normal spending).
>
> That's the difference between using a dataset as-is and actually doing
> feature engineering."

---

## Class Imbalance — Second Strongest Talking Point

> "With only 0.58% fraud, models trained normally just predict 'genuine'
> for everything. I used `class_weight='balanced'` for the sklearn models
> and `scale_pos_weight` for XGBoost, which reweights the loss function so
> the rare fraud class isn't ignored. Without this, my Logistic Regression
> model had 0% recall — it never once predicted fraud."

---

## Threshold Tuning — The Detail Most Student Projects Skip

> "By default, classifiers use a 0.5 probability cutoff to decide the
> class. That's an arbitrary choice — it doesn't account for how rare or
> costly fraud is. I scanned thresholds against the precision-recall curve
> and picked the one that maximizes F1-score on the test set, then used
> that tuned threshold — not 0.5 — in the live Flask app."

## Architecture Talking Points

- **Why SQLite, not just in-memory:** persistence across app restarts, and
  it's a real (if lightweight) database — demonstrates I can wire a model
  up to a data layer, not just a notebook.
- **Why Flask, not just a script:** shows the model deployed as a usable
  product, with a form, live dashboard, and API endpoint (`/api/live-stats`)
  — not just a Jupyter notebook with metrics printed at the bottom.
- **Why Joblib:** standard way to persist trained sklearn/XGBoost models so
  they don't need retraining on every app restart.
- **Why batch prediction, not just single-transaction:** real fraud systems
  score transactions in bulk (end-of-day settlement batches, backfills,
  re-scoring after a model update) — not one form submission at a time. I
  built both the single form and the CSV batch upload on top of the exact
  same `predict_dataframe()` function, so there's one source of truth for
  the prediction logic instead of duplicated code that could drift apart.

## Good Follow-Up Questions to Anticipate

**"Why not use SMOTE instead of class_weight?"**
> "class_weight/scale_pos_weight avoids generating synthetic data points,
> which keeps training faster and avoids the risk of SMOTE creating
> unrealistic synthetic fraud examples. SMOTE is a reasonable alternative
> and a natural next experiment — I list it in Future Improvements."

**"How would you deploy this in production?"**
> "Behind a proper WSGI server like Gunicorn, with the model served from a
> model registry rather than a local .pkl file, probably with a
> feature store for consistent feature computation between training and
> serving, and with monitoring for model drift over time since fraud
> patterns evolve."

**"What's a limitation of this project?"**
> "The live prediction form can't capture real merchant GPS coordinates or
> an exact transaction date, so `distance_km` and `day_of_week` are filled
> with dataset averages rather than computed live — in a real system, those
> would come straight from the payment gateway."

## If Asked to Whiteboard the Pipeline

```
Raw CSV (1.85M rows)
   → Clean (missing values)
   → Feature Engineering (age, distance_km, hour, day_of_week)
   → Encode categoricals (LabelEncoder: category, gender)
   → Train/test split (80/20, stratified)
   → Scale numeric features (StandardScaler)
   → Train 4 models with class-imbalance handling
   → Evaluate (Accuracy, Precision, Recall, F1, ROC-AUC, PR-AUC)
   → Select best model by F1
   → Tune decision threshold by F1 on PR curve
   → Save model + scaler + encoders + threshold (Joblib)
   → Flask app loads artifacts once at startup
   → /predict encodes+scales a new transaction, applies tuned threshold
   → Result + prediction logged to SQLite
   → Dashboard reads training summary (static) + SQLite (live)
```
